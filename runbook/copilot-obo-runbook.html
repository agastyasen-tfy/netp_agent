Before you start

What gets built, and what you need in hand.

The three identities you are about to create

Entra appWhat it isWho holds its secret
mcp-apiThe audience of your MCP server. The server rejects any token not minted for this ID. Exposes the delegated scope Tool.Write.Nobody — it never signs anything
agent-serviceThe audience the connector's token targets, and the credential the gateway uses to perform the OBO exchange. Exposes access_as_user.TrueFoundry (the MCP server entry's Auth Data)
agent-clientThe connector's own OAuth credentials. Its client ID arrives at the gateway as azp and is what the Agent Registry maps to your TrueFoundry agent.Power Apps (the connector's Security tab)

Token flow, in one breath

User signs in to Copilot Studio → the connector performs OBO exchange #1 and gets a token with aud = agent-service, oid = user, azp = agent-client → the gateway validates it, resolves the agent (azp) and the user (oid), checks RBAC → the gateway performs OBO exchange #2 as agent-service and gets a token with aud = mcp-api, same user → your MCP server validates that and runs the tool.

You need

Order matters. Phases 1 → 2 → 3 → 4 → 5 each consume an ID produced by the one before. Phase 2 (deploying the server) needs only the mcp-api ID from Phase 1a, so you can start it in a second tab once 1a is done.
1

Three app registrations

Entra admin center

Open entra.microsoft.com → left nav Identity → Applications → App registrations. Copy the Tenant ID from Overview into the worksheet first.

1a — mcp-api: the MCP server's audience

  1. Click + New registration. Name: mcp-api. Supported account types: Accounts in this organizational directory only. Leave Redirect URI empty. Click Register.
  2. On the Overview page, copy Application (client) ID → worksheet field mcp-api.
  3. Left nav Expose an API. Next to Application ID URI click Add, accept the default api://, click Save.
  4. Still on Expose an API, click + Add a scope:
    • Scope name: Tool.Write
    • Who can consent: Admins and users
    • Admin consent display name: Call tools as the signed-in user
    • Admin consent description: Allows tools to be invoked on behalf of the signed-in user.
    • State: Enabled → Add scope
  5. Left nav Manifest. Find "requestedAccessTokenVersion" (in the newer Microsoft Graph manifest editor it sits under "api"). Change its value from null to 2. Click Save.
Do not add any Authorized client applications on mcp-api. That is the passthrough recipe; in OBO the pre-authorization belongs on agent-service.

1b — agent-service: the connector's audience and the gateway's credential

  1. App registrations → + New registration. Name: agent-service. Single tenant. Register. Copy the Application (client) ID → worksheet field agent-service.
  2. Expose an API → Application ID URI Add → accept api:// → Save.
  3. + Add a scope: name access_as_user, Admins and users, display name Access the gateway as the signed-in user, any description, Enabled → Add scope.
  4. Same page, section Authorized client applications → + Add a client application. Client ID: fe053c5f-3692-4f14-aef2-ee34fc081cae (Microsoft's Azure API Connections service). Tick the access_as_user scope → Add application.
  5. Left nav API permissions → + Add a permission:
    • Tab APIs my organization uses → search mcp-api → select it → Delegated permissions → tick Tool.Write → Add permissions.
    • + Add a permission again → Microsoft Graph → Delegated permissions → search offline_access → tick → Add permissions.
  6. Left nav Manifest → set "requestedAccessTokenVersion" to 2 → Save.
  7. Left nav Certificates & secrets → Client secrets → + New client secret. Description truefoundry-gateway, pick an expiry → Add. Copy the Value column now — it is shown once. Park it somewhere safe; it goes into TrueFoundry in Phase 3c.
Without step 4, every tool call pops an interactive sign-in instead of a silent hand-off. It looks like a broken connector, not a missing grant.

1c — agent-client: the connector's credentials

  1. App registrations → + New registration. Name: agent-client. Single tenant. Under Redirect URI choose platform Web and enter https://global.consent.azure-apim.net/redirect. Register. Copy the Application (client) ID → worksheet field agent-client.
  2. API permissions → + Add a permission:
    • APIs my organization uses → search agent-service → Delegated → tick access_as_user → Add permissions.
    • Microsoft Graph → Delegated → offline_access → Add permissions.
  3. Certificates & secrets → + New client secret. Description power-apps-connector → Add. Copy the Value now. It goes into the Power Apps connector in Phase 4.
Delegated, never Application, for every permission in this chain. An Application permission validates fine and silently drops the user.

1d — Grant admin consent

  1. Open agent-service → API permissions → Grant admin consent for <tenant> → Yes. Both rows should show a green tick under Status.
  2. Open agent-client → API permissions → Grant admin consent → Yes.

Give it a minute to propagate before the first call. A missing grant surfaces later as AADSTS65001.

Deploy the demo MCP server

TrueFoundry

The server in mcp-obo-demo/ validates Entra JWTs (issuer, JWKS, aud = mcp-api, scp ∋ Tool.Write) and exposes add, subtract, echo and whoami. Push the folder to a Git repo first.

  1. In the TrueFoundry UI: Deployments → + New Deployment → Service. Pick the workspace to deploy into.
  2. Source: Git Repo. Choose the repository; if it is not listed, follow the link to connect your Git provider first. Branch: your default. Path to build context: the folder containing server.py (e.g. ./mcp-obo-demo/, or ./ if it is the repo root).
  3. Build: choose Dockerfile, path ./Dockerfile (relative to the build context). Or pick the Python build with requirements requirements.txt, Python 3.12, command python server.py.
  4. Ports: one port, 8000, protocol TCP, Expose on, and give it a host/endpoint. This URL is what the gateway will call.
  5. Environment variables (+ Add each):
    NameValue
    ENTRA_TENANT_ID
    MCP_API_APP_ID — bare GUID; Entra v2 tokens put the GUID, not api://…, in aud
    REQUIRED_SCOPETool.Write
  6. Resources: 0.2–0.5 CPU, 256–512 MB is plenty. Replicas 1. Click Submit.
  7. Wait for the build and rollout to go green. Open the service → copy its endpoint URL → worksheet field Deployed MCP server URL.
  8. Sanity check in a browser tab: /health should return {"status":"ok","audience":""}. Hitting /mcp without a token returns 401 — that is correct.

Prefer the CLI? pip install -U truefoundry && tfy login --host https://<control-plane>, then ENTRA_TENANT_ID=… MCP_API_APP_ID=… WORKSPACE_FQN=cluster:workspace python deploy.py from inside the folder.

Identity provider, agent, MCP server

TrueFoundry

Four entries: trust Entra tokens, register the mirror agent, store the agent-service secret, register the MCP server with the OBO exchange.

3a — Identity Provider (trust the connector's tokens)

  1. Settings → Security & Access → Identity Providers → + (Add Identity Provider).
  2. Fill in:
    FieldValue
    Enabledon
    Provider Nameentra-copilot
    Issuer URLhttps://login.microsoftonline.com//v2.0
    Allowed Audiencesapi:// and — add both spellings
    JWKS URIhttps://login.microsoftonline.com//discovery/v2.0/keys
    Resolve Token ToTrueFoundry user. Email Claim: preferred_username. Team Claim: groups (the form requires one; unused here).
  3. Save.
On the email claim. Entra v2 delegated tokens carry the UPN in preferred_username; email is present only if you add it as an optional claim. The gateway must resolve the signed-in user to an existing TrueFoundry user, so the UPN of whoever tests in Copilot Studio must match a TrueFoundry user's email. If your UPNs differ from your TrueFoundry emails, add the email optional claim to agent-service (Token configuration → Add optional claim → Access → email) and set Email Claim to email.

3b — Agent Registry entry (the mirror of the Copilot Studio agent)

  1. Agent Registry in the left nav → Create New Agent → Integrate a Remote Agent.
  2. Metadata: Agent Name , Description Mirror identity for the Copilot Studio demo agent (OBO via Power Apps connector). Next.
  3. Agent Identity: choose Identity provider-backed. Identity Provider: entra-copilot. Subject value: — the agent-client ID, because that is what arrives as azp. Next.
  4. Config: Embedded (Microsoft hosts the agent; the gateway sits in front of its tools, not in front of the agent). Next.
  5. Access Control: add yourself (and any teammates who will test in Copilot Studio) as collaborators with role Agent Access. This grant doubles as "whom the agent may act for" — a user without it gets a 403 at the gateway. Optionally enable Owner and pick your team. Submit.

3c — Store the agent-service secret

  1. Secrets in the left nav → open or create a Secret Group, e.g. copilot-obo.
  2. + Add Secret: key AGENT_SERVICE_CLIENT_SECRET, value = the agent-service secret you copied in Phase 1b step 7. Save.
  3. Copy the secret's FQN (looks like tfy-secret://<tenant>:copilot-obo:AGENT_SERVICE_CLIENT_SECRET).

3d — Register the MCP server with the OBO exchange

  1. MCP Gateway in the left nav → Add Server → Connect any Remote MCP Server.
  2. Fill in:
    FieldValue
    Nameobo-demo
    DescriptionDemo tools behind Entra OBO
    URL/mcp — your service, not the gateway
    Auth DataOAuth2
    OAuth ProviderMicrosoft Entra
    Grant TypeJWT Bearer (on-behalf-of) — not Token Exchange, which is the RFC 8693 shape Entra rejects
    Token URLhttps://login.microsoftonline.com//oauth2/v2.0/token
    Client ID — agent-service; must equal the inbound token's audience
    Client Secretthe FQN from 3c
    Scopesapi:///Tool.Write — names the destination
  3. Collaborators → + Add Collaborators → switch the picker to the Agents tab → pick → role MCP Server User. Keep yourself as MCP Server Manager. Save.
  4. Open the new server → How To Use tab. Copy the gateway URL. Split it: the host → worksheet Gateway host; everything from the first / onward → worksheet Gateway path.
If you ever rotate the agent-service secret, re-save this MCP server entry. Credentials bind on save; updating only the stored secret leaves the gateway using the old one.

The custom connector

Power Apps

Build it in Power Apps, not Copilot Studio's MCP onboarding wizard — the wizard has no on-behalf-of switch, so the user's identity would not carry through.

4a — Save this definition as obo-demo-connector.yaml

swagger: '2.0'
info:
  title: OBO Demo MCP
  description: Demo MCP tools via TrueFoundry MCP Gateway (on-behalf-of)
  version: '1.0.0'
host: 
basePath: /
schemes: [https]
paths:
  :
    post:
      summary: OBO demo MCP server
      operationId: InvokeMCP
      x-ms-agentic-protocol: mcp-streamable-1.0
      responses:
        '200':
          description: Success
Keep basePath: / and the whole path under paths:. Folding the path into basePath gives the same URL but puts the operation at the root path, which Power Platform does not register as an MCP operation. The connector imports, the connection succeeds, and the tool list is silently empty.
Prefer importing this file over building the connector from blank. The visual editor's "Add default response" generates responses: default: schema: type: string, which makes the runtime deserialise the MCP event stream as a string and breaks the handshake in Copilot Studio even though the Test tab passes. If you do build by hand, open the Swagger editor and make the response exactly '200': {description: Success} with no schema, and keep parameters empty.

4b — Import it

  1. Open make.powerapps.com. Top-right Environment picker → choose the same environment your Copilot Studio agent will live in.
  2. Left nav … More → Discover all → Custom connectors (pin it). Click + New custom connector → Import an OpenAPI file.
  3. Connector name: OBO Demo MCP. Import → pick the YAML → Continue.
  4. 1. General tab: Host should read , Base URL /. Leave the rest. Click Security →.

Resource URL is the field to get right. Point it at mcp-api and you have built passthrough instead. And only one resource may appear in Scope — Entra derives the audience from the resource of the requested scopes and rejects a request naming two; offline_access is resource-agnostic so it is fine alongside.
  1. Click Definition →. Under Actions you should see one action, InvokeMCP. Toggle Swagger editor on (top toolbar) and confirm x-ms-agentic-protocol: mcp-streamable-1.0 is still on the operation — some saves drop it.
  2. Click ✓ Create connector (top right). Wait for the save.
  3. Back on the Security tab, a read-only Redirect URL now shows. It must be https://global.consent.azure-apim.net/redirect, which you already registered on agent-client in Phase 1c. If it shows something else, add that exact URL to agent-client → Authentication → Web redirect URIs.

4d — Test and share

Do these steps in Power Apps, before Copilot Studio ever sees the connector. When Copilot Studio adds a custom connector to an agent it rewrites the connector's role assignments and creates the connection itself; done in the wrong order this can lock the maker out of their own connector and leave a connection that never obtains a token ("Unable to connect", with nothing in the gateway trace). Create the connection here, prove it with Test operation, then reuse that connection in Phase 5.
  1. 5. Test tab → + New connection. Expect the account picker and then either a short consent card or, if admin consent already covers it, an immediate "Connected". A full sign-in form with a password prompt means OBO is not active — recheck 4c.
  2. Still on Test, select the connection, click InvokeMCP under Operations, then Test operation. The request URL is a …powerplatform.com/connectors/runtime/invoke/… proxy ending in your gateway path — that is normal. The response should be a 400 with Invalid JSON-RPC request: the empty body is rejected by the gateway's protocol layer, which only runs after authentication passed. A 401 here means the token did not resolve at the gateway (see Troubleshooting).
  3. Back on the connector list, click ⋯ → Share next to OBO Demo MCP. Add the users who will test the agent with Can view; makers who will edit it get Can edit. Not needed for yourself — the owner can always use their own connector.
5

The agent

Copilot Studio

Open copilotstudio.microsoft.com. Top-right environment picker → the same environment as the connector.

  1. Left nav Create → + New agent. Either describe it or click Skip to configure. Name: OBO Demo. Instructions: You have tools from the OBO Demo MCP server. Use them whenever a user asks to add, subtract, echo text, or asks who they are. Always call whoami when asked about identity; never guess. Click Create.
  2. Settings (top right) → Generative AI → Orchestration: Generative. Save. Do this before attaching the tool — with classic orchestration the agent never calls MCP tools; the tool appears attached and is silently ignored.
  3. Top tab Tools → + Add a tool. Your connector appears under Model Context Protocol (Copilot Studio files tools by protocol; the x-ms-agentic-protocol flag is what puts it there). Search OBO Demo MCP → select it. Do not use New tool → Model Context Protocol, which is the wizard that builds its own connector without on-behalf-of.
  4. When asked for a connection, choose the existing connection you created in Power Apps (Phase 4d) rather than creating a new one. Then Add to agent.
  5. Open the tool from the Tools list. Under its tools you should see add, subtract, echo and whoami. Empty list → see Troubleshooting row 1.
  6. Still in the tool's settings, confirm end-user authentication is set so each user connects with their own credentials (the default for OAuth connectors), and Save.
Attach only one connector to this agent. An agent with both a passthrough and an OBO connector sees two sets of identically-named tools and picks between them unpredictably.
6

Prove the chain

Copilot Studio TrueFoundry

Use the Test pane on the right of the agent.

  1. Type Who am I according to your tools? The agent should call whoami and report your UPN, name and object ID, with mode: delegated, aud = mcp-api and actor_app = agent-service. That is the whole OBO story in one tool result: your identity travelled two exchanges and arrived intact, and the app that last exchanged was the gateway's agent-service.
  2. Type Add 41 and 1. Expect 42.
  3. In TrueFoundry, open the MCP server obo-demo → its request logs / audit. Each call should show both the agent and your user as the caller.
  4. Negative test: in the Agent Registry entry's Access Control, remove your Agent Access row and save. Ask the agent to add numbers again → it should fail with a gateway 403. Restore the grant.
  5. Negative test #2: in Phase 3d's MCP server, temporarily remove the agent collaborator → 403 again. Restore it.

Those two 403s are the point of the exercise. The connector's token is audienced to agent-service, which your MCP server refuses outright, so the only route to the tools is through the gateway — and the gateway will only pass calls from a registered agent, acting for a user that agent is allowed to act for.

Test with a real Entra token instead (Azure CLI against api://<agent-service>/access_as_user, with the CLI app id 04b07795-8ddb-461a-bbee-02f9e1bf7b46 temporarily mapped on the agent), or proceed to Copilot Studio.
Server log: missing required scopes (has ['Tool.write'…], requires ['Tool.Write'])The scope on mcp-api was created with different casing. Entra matches scope names case-insensitively and returns the stored spelling; the server compares exactly. Set REQUIRED_SCOPE on the server to the spelling Entra returns, or recreate the scope.
Power Apps: "You do not have permissions to edit this connector" right after adding it to an agentCopilot Studio rewrote the connector's role assignments. Re-grant yourself with Set-AdminPowerAppConnectorRoleAssignment … -RoleName CanEdit from the PowerApps admin PowerShell module, or import a fresh connector and follow the 4d ordering. Recreate the connection from the Power Apps Test tab as the connector owner and confirm with Test operation (expect a 400 Invalid JSON-RPC request), then re-add the tool choosing that connection.
8

Variant: agent hosted in your own environment

Entra TrueFoundry

For customers who cannot use Copilot Studio (on-prem, no inbound path from Microsoft's cloud). Same MCP server, same gateway setup, same governance; the agent runs as a TrueFoundry Service in the customer's cluster and carries its own Entra identity. Code: the mock-agent/ folder.

What changes, what doesn't

Phases 1–3 stay as they are: mcp-api, agent-service, the Identity Provider and the MCP server registration are reused unchanged, and the gateway still exchanges as agent-service. Phases 4–5 (Power Apps and Copilot Studio) are replaced by the mock agent. Because this agent is custom-hosted it can do what Copilot Studio cannot: present its own Entra identity to the gateway, in a second header, alongside the user's.

Every call carries two bearer tokens, both audienced to agent-service: the user's in Authorization (obtained by device-code sign-in) and the agent's in x-tfy-agent-authorization (client credentials). The gateway resolves the agent from the second token's azp, the user from the first, checks the agent may act for that user and may reach the server, then runs the same OBO exchange.

8a — Entra: one extra app registration, mock-agent

  1. App registrations → + New registration. Name mock-agent, single tenant, no redirect URI → Register. Copy the Application (client) ID.
  2. Authentication → Advanced settings → Allow public client flows: Yes → Save. Device-code sign-in requires it.
  3. API permissions → + Add a permission → APIs my organization uses → agent-service → Delegated → access_as_user; and Microsoft Graph → Delegated → offline_access. Then Grant admin consent.
  4. On agent-service → Expose an API → Authorized client applications → + Add: the mock-agent client ID, tick access_as_user.
  5. Certificates & secrets → + New client secret → copy the value. It goes into a TrueFoundry Secret in 8b; it is the agent's own credential.

8b — TrueFoundry

  1. Secrets: add AGENT_CLIENT_SECRET with the value from 8a step 5; copy its tfy-secret:// FQN.
  2. Agent Registry → Create New Agent → Integrate a Remote Agent: name netapp-mock-agent; Identity Identity provider-backed, provider entra-copilot, Subject value = the mock-agent client ID; Config Embedded; Access Control: the users who will sign in, as Agent Access. (Or add the ID as a second mapping on the Phase 3b agent.)
  3. MCP Gateway → your MCP server (aga-obo-demo) → Collaborators: add agent:netapp-mock-agent as MCP Server User.
  4. The model the agent will use (e.g. openai-main) → Collaborators: add the agent and the users. Or set LLM_GATEWAY_API_KEY in the deploy to a TrueFoundry API key and skip this.
  5. Deploy from the mock-agent/ folder with python deploy.py (see its docstring for the env vars; AGENT_CLIENT_SECRET_FQN is the secret reference, never the value). Open https://<HOST>.

8c — Demo script

  1. Sign in with Microsoft (device code). Click Show token claims: two tokens, both aud = agent-service; the user's carries preferred_username, the agent's carries azp = mock-agent and no user.
  2. Ask Who am I according to your tools? The trace shows whoami through the gateway; the result names the signed-in user with mode: delegated, actor_app = agent-service, aud = mcp-api.
  3. TrueFoundry traces for the server: every call shows agent = netapp-mock-agent and the user.
  4. Remove the user's Agent Access on the agent → next tool call is a gateway 403. Restore. Remove the agent's MCP Server User role → 403 again. The agent and the MCP server were not touched; the gateway is the control point.
  5. Optional: sign in as a second user without Agent Access → 403 on the first call. Same agent, different person, different answer.
Why this is the stronger demo. With Copilot Studio the agent's Entra identity never reaches the gateway; a connector app stands in for it. Here the agent's own app ID arrives in azp of the agent token, so the registry mapping, the audit trail and the 403s are about the actual agent, not a proxy. That is the Agent ID story the customer asked for.
